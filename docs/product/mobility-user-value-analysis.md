# 서울시 실시간 데이터 기반 이동 안내 사용자 가치 분석

- 작성일: 2026-09-11
- 분석 대상: `POST /v1/mobility-decisions`와 프론트 이동 안내 화면
- 분석 관점: 현재 코드 기준의 제품 가치, 데이터 활용도, 의사결정 지원 수준

## 1. 요약

현재 서비스는 서울 특정 지역의 혼잡도, 추정 인구, 날씨, 도로 소통 상태를 확인하는 **지역 상황 브리핑**으로는 가치가 있다. 사용자 상태와 선호도 일부 반영되므로 단순 데이터 조회보다 한 단계 발전한 형태다.

그러나 출발지·도착지, 실제 경로, 거리, 소요시간, 비용, 환승 정보가 없으므로 사용자가 어떤 교통수단을 이용할지 최종 결정하도록 돕는 기능은 제한적이다. 현재 구현을 기준으로 한 종합 사용자 가치는 약 **5/10**으로 평가한다. 이 점수는 실제 사용자 조사나 운영 지표가 아니라 코드와 화면을 검토한 정성 평가다.

또한 현재 통합 API의 교통수단 선택은 OpenAI가 아니라 Java 규칙 엔진이 수행한다. 따라서 서비스 표현은 “AI가 최적 교통수단을 결정한다”보다 “실시간 지역 상황과 사용자 조건을 반영해 이동수단을 안내한다”가 정확하다.

| 평가 영역 | 현재 수준 | 판단 |
|---|---:|---|
| 혼잡·날씨·도로 상황 확인 | 높음 | 관측값, 상태, 시각, 출처를 함께 제공한다. |
| 사용자 상태 반영 | 보통 | 안전 제약과 일부 우선순위에 반영되지만 규칙이 단순하다. |
| 실제 이동수단 비교·결정 | 낮음 | 경로별 시간·거리·비용 비교가 없다. |
| AI 고유의 추가 가치 | 매우 낮음 | 현재 통합 API 경로에서는 OpenAI를 호출하지 않는다. |
| 전체 사용자 가치 | 약 5/10 | 브리핑에는 유용하지만 최종 이동 결정 도구로는 부족하다. |

## 2. 현재 동작 구조

```text
사용자
  -> 상태 0~1개, 선호, 이용 가능 수단, 목적, 서울 지역 선택
  -> POST /v1/mobility-decisions
  -> MobilityRestController
  -> MobilityRecommendationService
  -> TrafficDataProvider
      -> MCP 또는 서울시 REST API
      -> MCP 실패 시 REST fallback 가능
  -> CitySituation 정규화
  -> Java 규칙 기반 교통수단 선택
  -> MobilityResponse
  -> 프론트 결과 카드
```

통합 API 진입점은 [`MobilityRestController`](../../src/main/java/com/example/musinsaPointSystem/data/apiController/MobilityRestController.java)이며, 실제 판단은 [`MobilityRecommendationService`](../../src/main/java/com/example/musinsaPointSystem/data/apiService/MobilityRecommendationService.java)의 `chooseMode()`에서 수행한다.

[`MobilityAgentService`](../../src/main/java/com/example/musinsaPointSystem/data/apiService/MobilityAgentService.java)와 OpenAI 연동 코드는 남아 있지만 현재 통합 API 호출 흐름에는 연결되어 있지 않다.

## 3. 현재 사용자에게 제공하는 정보

### 3.1 실시간·관측 정보

- 지역 혼잡 단계와 설명
- 추정 인구 최소·최대 범위
- 기온, 날씨 상태, 강수 형태, 습도
- 도로 소통 단계와 평균 속도
- 미세먼지·초미세먼지 정보
- 날씨 예보와 혼잡도 예보
- 지하철역, 버스정류장, 따릉이 대여소, 주차장, 전기차 충전소 수
- 각 데이터의 관측 시각과 출처
- `LIVE`, `STALE`, `UNAVAILABLE` 상태

### 3.2 사용자 입력

- 사용자 상태: 피곤함, 짐 소지, 보행 제한, 아이 동반, 심야
- 선호: 혼잡 회피, 날씨 노출 최소화, 도로 지연 회피, 특정 수단 선호
- 현재 이용 가능한 교통수단
- 이동 목적: 출근, 퇴근, 외출, 관광 등
- 분석할 서울 지역

### 3.3 추천 결과

- 우선 고려할 이동수단
- 혼잡 시 출발 지연 제안
- 관측 데이터, 사용자 상태, 사용자 선택, 시스템 판단 근거
- 추천에 반영한 요소
- 데이터 한계와 현장 차이 경고

## 4. 현재 가치가 있는 부분

### 4.1 정보의 신선도와 한계를 숨기지 않는다

관측 시각과 `LIVE`, `STALE`, `UNAVAILABLE` 상태를 구분한다. 조회 실패나 오래된 데이터를 현재 사실처럼 보여주지 않는 구조는 신뢰성 측면에서 가치가 높다.

### 4.2 실제 관측과 판단을 구분한다

응답의 `evidence`는 관측값, 사용자 상태, 사용자 선호, 시스템 판단을 구분한다. 사용자는 추천 이유를 확인할 수 있고 개발자는 잘못된 판단의 원인을 추적할 수 있다.

### 4.3 일부 안전·편의 조건이 실제 규칙에 반영된다

- 보행 제한 상태에서는 도보와 자전거를 제외한다.
- 짐 소지 또는 아이 동반 상태에서는 자전거를 제외한다.
- 피곤함이나 보행 부담이 있으면 저노력 이동수단을 우선한다.
- 심야에는 택시·자동차·전기차를 우선 검토한다.
- 비·눈이 관측되고 날씨 노출 최소화를 선택하면 지붕이 있는 수단을 우선한다.
- 도로가 지연되거나 사용자가 도로 지연 회피를 선택하면 대중교통을 우선한다.
- 혼잡 회피를 선택하고 이후 혼잡도가 낮아질 것으로 관측되면 늦은 출발을 제안한다.

### 4.4 MCP 장애가 전체 기능 중단으로 바로 이어지지 않는다

[`TrafficDataProviderRouter`](../../src/main/java/com/example/musinsaPointSystem/data/traffic/TrafficDataProviderRouter.java)는 설정에 따라 MCP를 사용하고, 실패하면 서울시 REST API로 fallback할 수 있다. 사용자 입장에서는 데이터 제공 경로보다 결과의 지속성이 중요하므로 합리적인 장애 정책이다.

## 5. 사용자 가치가 제한되는 핵심 원인

### 5.1 출발지·도착지와 실제 경로가 없다

현재 요청은 특정 지역의 상황을 분석할 뿐 실제 이동 경로를 계산하지 않는다. 다음 정보를 제공할 수 없다.

- 목적지까지 거리와 예상 소요시간
- 교통수단별 경로와 도착 예정 시각
- 도보 거리와 환승 횟수
- 요금과 택시 예상 비용
- 경로별 실시간 지연
- 역·정류장까지 접근 시간

결국 사용자는 추천을 받은 뒤 별도 지도나 길찾기 서비스를 다시 열어야 한다. 이것이 최종 의사결정 도구로 발전하는 데 가장 큰 제약이다.

### 5.2 이동 목적 반영 범위가 제한적이다

현재 입력 목적은 출근, 퇴근, 외출로 제한했다. 목적은 설명 근거에 포함되지만 목적별 추천 정책은 아직 세분화되지 않아 다른 조건이 같으면 같은 결과가 나올 가능성이 높다.

| 목적 | 필요한 우선순위 |
|---|---|
| 출근 | 도착시간, 지연 위험, 정시성 |
| 퇴근 | 피로도, 편안함, 비용 |
| 관광 | 도보 경험, 주변 장소, 이동 편의 |
| 심야 이동 | 안전, 막차, 심야버스, 택시 가능성 |

### 5.3 추천 기본값이 대중교통에 치우쳐 있다

특별한 조건이 없고 대중교통이 허용되면 대부분 대중교통이 선택된다. 서울시 데이터를 조회했더라도 관측값이 최종 결과를 바꾸지 않는 경우가 많아 사용자는 개인화가 약하다고 느낄 수 있다.

### 5.4 하나의 수단만 제시하고 대안을 비교하지 않는다

현재 결과는 하나의 교통수단을 우선 제안한다. 사용자가 결정하려면 최소 2~3개 대안에 대한 시간, 거리, 비용, 도보, 환승, 신뢰도를 비교할 수 있어야 한다.

### 5.5 주변 시설 정보가 행동으로 연결되지 않는다

시설 개수만으로는 실제 이동 가능성을 판단하기 어렵다. “따릉이 대여소 3곳”보다 가장 가까운 대여소까지 거리, 대여 가능 자전거 수, 반납 가능 거치대 수가 더 중요하다.

### 5.6 안내 문구가 일반적이고 내부 코드가 노출된다

요약 문장은 대부분 고정된 일반 문구이며 `TIRED`, `LIMITED_WALKING` 같은 enum 값이 추천 반영 요소로 노출될 수 있다. 일반 사용자에게는 자연스러운 한국어와 구체적인 수치 기반 이유가 필요하다.

### 5.7 심야 추천에 필요한 실시간 검증이 없다

심야 상태에서는 택시나 자동차를 우선하지만 막차, 심야버스, 택시 비용과 호출 가능성, 사용자의 운전 가능 여부, 주차 가능성을 확인하지 않는다.

### 5.8 사고·재난·통제 정보가 비어 있다

응답과 프론트에는 `alerts` 구조가 있지만 현재 백엔드는 항상 빈 배열을 반환한다. 지하철 장애, 도로 통제, 행사, 재난은 실제 교통수단 선택을 크게 바꾸는 정보이므로 연결 가치가 높다.

## 6. MCP와 AI에 대한 판단

### 6.1 MCP는 데이터 연결 방식이지 사용자 가치 그 자체가 아니다

기본 설정은 `MCP_CLIENT_ENABLED=false`, `TRAFFIC_PROVIDER=public-api`다. 운영 환경변수를 설정하지 않으면 서울시 REST API를 사용한다. MCP를 활성화해도 현재 내부 모델과 프론트 응답은 동일하다.

사용자 가치에 직접 영향을 주는 요소는 데이터 최신성, 제공 범위, 결측률, 응답시간, 장애·fallback 비율과 관측 데이터가 추천을 실제로 바꾸는 정도다.

### 6.2 현재 통합 API에는 AI 고유 가치가 없다

현재 교통수단은 규칙 엔진이 결정하므로 OpenAI의 설명·추론 능력이 사용자 결과에 추가되지 않는다. 화면이나 홍보 문구에서 “AI가 최적 교통수단을 결정한다”고 표현하면 실제 구현과 차이가 생긴다.

### 6.3 권장 AI 역할

AI가 검증되지 않은 수치나 경로를 생성하게 해서는 안 된다.

- 규칙 엔진과 경로 API가 계산한 상위 대안 설명
- 사용자 상태에 맞는 설명 순서와 표현 조정
- 대안별 장단점 요약
- 결정에 필요한 누락 정보 질문
- 관측값과 추천의 관계를 자연어로 설명

최종 수단, 거리, 시간, 요금은 검증 가능한 경로 API와 정책 엔진이 결정해야 한다.

## 7. 이번 백엔드 개선 반영 사항

- 사용자 상태는 기존 `UserState` enum을 유지하고 요청당 정확히 1개로 제한
- 목적, 사용자 상태, 선호, 이동수단 enum에 한국어 표시명 추가
- `strategyCode`, evidence type, limitation code, alert severity/status를 enum으로 타입화
- 프론트와 동일하게 이동 목적을 출근·퇴근·외출 enum으로 제한
- 고정 summary를 목적·상태·혼잡·도로·날씨 기반의 동적 설명으로 교체
- priorities와 evidence에 내부 enum 원문 대신 한국어 표시명 사용

API의 enum JSON 값은 기존 문자열과 동일하므로 프론트 계약은 유지된다. 거리·시간·비용, 실시간 운행과 재난 정보는 외부 데이터 계약이 없어 이번 범위에 포함하지 않았다.

## 8. 권장 개선 로드맵

### P0 — 사용자 결정에 필요한 핵심 데이터

1. 출발지와 도착지 입력 추가
2. 길찾기 API를 통한 수단별 거리·시간·경로 확보
3. 도보 거리, 환승 횟수, 요금, 도착 예정 시각 제공
4. 이동 목적을 추천 정책에 실제 반영
5. 결과에 2~3개 대안과 비교 근거 제공

### P1 — 실행 가능성과 신뢰도 강화

1. 막차·심야버스와 대중교통 도착 정보 연결
2. 따릉이 재고, 주차 잔여 공간, 충전기 사용 가능 상태 연결
3. 사고·재난·행사·도로 통제 alert 연결
4. 추천 점수와 데이터 부족에 따른 신뢰도 표시
5. enum을 사용자 친화적인 한국어로 변환

### P2 — AI 설명 계층 추가

1. 정책 엔진이 계산한 후보와 evidence만 AI 입력으로 전달
2. 구조화 출력과 허용된 evidence ID 검증
3. 거리·시간 등 제공되지 않은 수치 생성 금지
4. AI 장애 시 규칙 기반 결과 그대로 제공
5. AI 설명과 원본 관측값을 화면에서 구분

## 9. 목표 결과 예시

```text
1순위 지하철
- 예상 34분, 도보 8분, 환승 1회
- 도로 정체 영향을 적게 받음
- 사용자의 도로 지연 회피 선호 반영

2순위 택시
- 예상 29~42분, 예상 비용 18,000원
- 현재 도로 서행으로 도착시간 변동 가능

3순위 자전거
- 비 예보와 사용자 상태를 고려해 권장하지 않음
```

이 형태는 추천 수단만 제시하는 것보다 사용자가 자신의 비용·시간·편의 우선순위에 따라 최종 선택할 수 있게 한다.

## 10. 사용자 가치 검증 지표

### 제품 지표

- 추천 요청 완료율
- 결과 화면과 상세 화면 조회율
- 추천 후 특정 이동수단 선택률
- 다시 분석하기 비율
- “도움이 됐어요/안 됐어요” 응답
- 추천과 실제 사용자 선택의 일치율

### 품질·운영 지표

- `LIVE`, `STALE`, `UNAVAILABLE` 비율
- MCP 성공률과 REST fallback 비율
- API 응답시간 P50/P95/P99
- 목적·사용자 상태별 추천 분포
- 특정 수단으로 추천이 과도하게 집중되는 비율
- 관측 근거와 추천이 모순되는 사례 수

### 권장 검증 방법

기존 지역 브리핑과 경로·대안 비교가 포함된 개선 화면을 A/B 테스트한다. 추천 수단 클릭률뿐 아니라 사용자가 실제 이동 결정을 완료했는지와 결과가 도움이 되었는지를 함께 측정해야 한다.

## 11. 보안 및 운영 주의사항

분석 과정에서 Git이 추적하는 `application-local.yml`에 실제 형식의 OpenAI API Key가 직접 입력된 상태를 확인했다. 비밀값은 문서에 기록하지 않았으며 파일도 수정하지 않았다.

권장 조치는 현재 키 폐기 및 재발급, `OPENAI_API_KEY` 환경변수 또는 비밀 저장소로 이동, Git 이력 확인, 기본 비밀값 제거, 로그·오류 응답의 키 마스킹이다.

## 12. 최종 판단

현재 서비스의 정확한 제품 정의는 다음과 같다.

> 사용자 상태를 일부 반영하여 서울 지역의 실시간 혼잡·날씨·도로 정보를 설명하고, 고려할 이동수단을 안내하는 서비스

현재 단계에서는 다음 표현은 피하는 것이 좋다.

> AI가 목적지까지 가장 좋은 교통수단을 결정해주는 서비스

출발지·도착지와 교통수단별 시간·거리·비용을 확보하고 목적별 정책과 대안 비교를 추가하면, 지역 데이터 조회 서비스에서 실질적인 이동 의사결정 지원 서비스로 발전할 수 있다.
