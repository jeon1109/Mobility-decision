# Mobility Decision 제품 기획서 — 변경 반영본

- 작성일: 2026-09-13
- 이전 문서 기준일: 2026-09-11
- 기준: 현재 백엔드·프론트 구현
- 공식 API: `GET /v1/mobility/context`, `POST /v1/mobility/decisions`

## 1. 개정 결론

현재 서비스는 이전의 한 화면짜리 지역 상황 안내에서 다음 3단계 흐름으로 발전했다.

```text
1. 출발 조건
   - 서울 출발 지역
   - 이동 목적
   - 이동 우선순위
        ↓
2. 출발 지역의 현재 상황
   - 날씨, 혼잡도·추정 인구, 도로, 인근 지하철
   - 관측시각·수집시각·출처·신선도
        ↓
3. 목적지 입력
        ↓
규칙 기반 이동수단 안내
```

사용자 흐름과 데이터 신뢰성은 개선됐지만 목적지까지의 실제 경로·거리·소요시간·요금은 계산하지 않는다. 목적지는 현재 추천 계산의 입력이 아니라 결과 설명에 표시되는 문자열이다.

현재 제품의 정확한 정의:

> 서울 출발 지역의 실시간 상황을 먼저 확인하고, 이동 목적과 우선순위를 받아 고려할 이동수단을 규칙 기반으로 안내하는 서비스

아직 사용하면 안 되는 표현:

> AI가 목적지까지 최적 경로와 교통수단을 계산해 주는 서비스

## 3. 현재 가치와 한계

### 좋아진 점

1. 사용자가 출발 지역 상황을 먼저 확인한다.
2. 관측시각과 서버 수집시각, 출처와 freshness를 구분한다.
3. 오래된 데이터와 기준시각을 알 수 없는 데이터를 구별한다.
4. MCP Traffic 실패 시 다른 Context를 살리고 REST fallback을 사용할 수 있다.
5. 결과 화면이 실제 경로를 제공하지 않는다고 명시한다.
6. 사용자 입력을 네 가지 일반 언어 우선순위로 단순화했다.

### 남은 한계

1. 목적지 좌표 변환과 경로 탐색이 없다.
2. 수단별 시간·거리·요금·환승·도보를 비교하지 못한다.
3. 목적지 문자열은 결과 문구에만 붙고 추천 수단을 바꾸지 않는다.
4. 이동 목적은 요약에만 표시되고 `chooseMode()` 정책에 사용되지 않는다.
5. 새 흐름은 사용자 상태를 빈 목록으로 변환하므로 짐·보행 제한·아이·심야 규칙이 동작하지 않는다.
6. `alerts`는 구조만 있고 항상 빈 목록이다.
7. 공식 통합 API는 Spring AI가 아니라 Java 규칙 엔진으로 판단한다.
8. 추천 수단 한 가지만 제시하고 대안을 비교하지 않는다.

## 5. 기획·구현 불일치와 확정 권고

### 이동 목적

이전 확정 선택지는 **출근·퇴근·외출**이지만 현재 프론트는 **출근·귀가·약속·여행·기타**다. 백엔드는 `OUTING`을 포함해 더 많은 enum을 유지한다.

권장안:

- 화면: 출근, 퇴근, 외출
- API: `COMMUTE_TO_WORK`, `GO_HOME`, `OUTING`
- `GO_HOME` 표시 문구를 제품 용어인 “퇴근”으로 통일
- 기존 enum은 API 사용 여부 확인 후 단계적으로 정리

### 사용자 상태

과거에는 다섯 상태 중 한 개를 필수 선택했지만 새 화면에서는 제거됐다. 이번 개정은 입력 부담을 줄인 현재 흐름을 기준으로 **MVP에서 제외**한다. 접근성과 안전 개인화가 핵심이 되면 과거 컴포넌트를 그대로 복원하지 말고 “이동 제약” 한 항목으로 다시 설계한다.

### 이동 우선순위

현재 네 항목을 1~4개 모두 선택할 수 있다. 전부 선택하면 우선순위 의미가 약해진다.

권장안:

- 최소 1개, 최대 2개
- 순서가 중요하면 1순위·2순위로 명시
- 더 단순한 MVP가 필요하면 단일 선택 검토

### 지도 버튼

이전 요구에서는 지도 기능 제거를 결정했지만 결과 화면에 “주변 지도에서 확인” 버튼이 남아 있다. 현재 링크는 목적지가 아니라 출발 지역명을 검색한다.

권장안:

- 현재 버튼 제거
- 실제 경로 Provider 도입 후 “길찾기 열기” 필요성을 다시 결정

### API 경로

- 공식 경로: `POST /v1/mobility/decisions`
- 기존 호환 경로: `POST /v1/mobility-decisions`

슬래시 기반 경로를 공식 API로 사용한다. 기존 경로는 Deprecated로 문서화하고 호출 로그가 없음을 확인한 후 제거한다.

## 6. 개정 MVP 범위

### 사용자 입력

- 출발 지역: 서울시 제공 목록에서 필수 선택
- 이동 목적: 출근·퇴근·외출 중 하나
- 이동 우선순위: 빠르게·저렴하게·덜 걷기·혼잡 피하기 중 1~2개
- 목적지: 필수
- 사용자 상태와 이용 가능 수단: MVP 입력에서 제외

### 현재 상황 결과

- 날씨와 기온
- 혼잡 단계와 추정 인구
- 도로 소통과 평균 속도
- 인근 지하철 정보
- 관측시각, 수집시각, 출처, freshness
- 오래되거나 없는 데이터 경고

### 이동 안내 결과

경로 Provider 전에는 다음만 제공한다.

- 고려할 이동수단 한 가지
- 목적지와 우선순위
- 추천 근거와 데이터 한계
- 실제 노선·시간·비용 미제공 안내

경로 데이터가 없을 때 “최적”, “가장 빠름”, “예상 도착시간”이라는 표현을 사용하지 않는다.

## 7. 최우선 P0: 경로 기반 의사결정

### 목적지 정규화

- 목적지 문자열을 장소 검색 Provider에 전달
- 위도·경도와 정규화된 장소명 확보
- 동명 장소가 여러 개면 사용자 선택
- 검색 실패 시 명확한 오류

### 경로 후보

최소 대중교통, 자동차/택시, 도보 후보를 실제 Provider에서 조회한다. 자전거는 데이터 범위를 확인한 후 추가한다.

각 후보에 필요한 값:

- 총 예상 시간과 거리
- 도보 시간과 거리
- 환승 횟수
- 예상 요금 또는 비용 범위
- 예상 도착시각
- 조회시각과 출처

### 정책 엔진

| 조건 | 실제 평가 기준 |
|---|---|
| 출근 | 정시성, 시간, 지연 변동성 |
| 퇴근 | 피로 부담, 도보, 비용 |
| 외출 | 시간·비용·편의 균형 |
| 빠르게 | 총 소요시간 최소 |
| 저렴하게 | 총비용 최소 |
| 덜 걷기 | 도보 거리 최소 |
| 혼잡 피하기 | 혼잡 노출 최소 |

실제 경로 후보에 점수를 매겨 상위 2~3개를 반환한다. 특정 조건에서 무조건 대중교통을 반환하는 방식은 줄인다.

### 목표 화면 예시

```text
1순위 대중교통
- 38분 · 1,500원 · 도보 7분 · 환승 1회
- 도로 정체 영향을 적게 받음

2순위 택시
- 31~45분 · 약 18,000원
- 현재 도로 지연으로 도착시간 변동 가능

3순위 도보
- 72분 · 비용 없음
- “빠르게” 우선순위와 맞지 않아 낮은 순위
```

Provider에서 검증된 값만 표시한다. 값이 없으면 AI나 프론트가 추정해 채우지 않는다.

## 8. MCP와 AI의 역할

MCP는 서울시 데이터를 가져오는 연결 방식이다. 사용자 가치는 최신성, 결측률, 응답시간, fallback 성공률과 추천에 실제로 반영되는 정도로 평가한다.

현재 공식 Mobility API에는 Spring AI가 연결돼 있지 않다. 향후 AI는 다음에만 사용한다.

- 정책 엔진이 만든 후보의 장단점 설명
- 목적과 우선순위에 맞는 표현 순서 조정
- evidence 자연어 요약
- 꼭 필요한 누락 정보 질문

AI가 경로·거리·시간·요금·실시간 상태를 생성하게 하지 않는다. AI 장애 시 규칙 기반 후보와 원본 데이터는 그대로 제공한다.

## 9. 오류와 fallback

| 상황 | 사용자 동작 |
|---|---|
| Context 일부 실패 | 확보한 정보 표시, 누락 영역은 “정보 없음” |
| MCP Traffic 실패 | REST fallback, 실제 출처 표시 |
| Context 전체 실패 | 다음 단계 차단 및 재시도 |
| 목적지 검색 실패 | 재입력 또는 장소 후보 선택 |
| 일부 수단 경로 실패 | 성공 후보만 표시하고 누락 이유 안내 |
| 모든 경로 실패 | 지역 상황 유지, 길찾기 실패 안내 |
| AI 설명 실패 | 규칙 기반 결과 정상 반환 |

Webhook이 제거된 현재는 분석 대기·콜백 상태를 사용자에게 노출하지 않는다.

## 10. 데이터와 트랜잭션

- 출발지와 목적지는 이동 패턴을 드러낼 수 있어 로그와 보관을 최소화한다.
- 현재 추천 결과는 DB에 저장하지 않는다.
- 저장이 확정되면 외부 호출 완료 후 별도 Persistence UseCase에서 짧게 저장한다.
- MCP·경로 API·Spring AI 호출 동안 DB 트랜잭션을 열지 않는다.
- 캐시와 향후 이벤트는 DB 커밋 이후 처리한다.
- 적용된 Flyway Migration은 변경하지 않고 후속 버전을 추가한다.

## 12. 실행 순서

### 1차 — 기획 불일치 정리

1. 목적을 출근·퇴근·외출로 통일
2. 우선순위 최대 선택 수 확정
3. 지도 버튼 제거
4. 사용하지 않는 상태·이동수단 컴포넌트 보존/삭제 결정
5. 공식 API와 Deprecated 경로 문서화

### 2차 — 경로 기반 MVP

1. 장소 검색 Port/Adapter
2. 경로 조회 Port/Adapter
3. 목적·우선순위 점수 정책
4. 상위 2~3개 후보 응답 계약
5. 비교 결과 화면

### 3차 — 신뢰도와 운영

1. 사고·통제·재난 Alert
2. 대중교통·시설 가용성 확대
3. Provider timeout, retry, circuit breaker, 메트릭
4. 사용자 피드백 기반 정책 개선

### 4차 — AI 설명

1. 검증된 후보와 evidence만 AI 입력
2. 구조화 출력과 evidence ID 검증
3. 수치 생성 금지
4. AI 실패 fallback

## 13. 기획 완료 조건

- 제품 설명과 실제 구현이 일치한다.
- 목적과 우선순위 정책이 백엔드·프론트에서 동일하다.
- 목적지가 실제 장소 검색과 경로 계산으로 이어진다.
- 최소 2개 후보의 시간·거리·비용·도보·환승을 비교한다.
- 모든 수치는 출처와 조회시각을 갖는다.
- 없는 값을 임의 생성하지 않는다.
- AI와 규칙 엔진의 책임을 구분한다.
- 장애 시 부분 결과와 재시도 동작이 정의된다.

## 14. 최종 판단

이번 변경으로 데이터 신뢰성과 사용자 진행 흐름은 좋아졌다. 그러나 목적지를 입력받는 것과 목적지까지의 경로를 계산하는 것은 다르다. 현재는 목적지 문자열을 표시하는 수준이다.

권장 개발 순서:

> 기획 불일치 정리 → 장소·경로 데이터 연동 → 후보 비교 정책 → 운영 신뢰성 → AI 설명

AI보다 먼저 검증 가능한 시간·거리·비용을 확보하는 것이 사용자 의사결정에 더 큰 가치를 준다.
