# Mobility Decision v2 Phase 2 결과

## 완료 범위

Phase 1 설계를 기준으로 기존 기능을 보존하면서 추천 전 사용자 흐름을 3단계로 개편했다.

1. 출발지, 이동 목적, 우선순위 입력
2. 출발지의 현재 교통·날씨·혼잡 상황 확인
3. 도착지 입력 후 추천 요청 및 결과 확인

현재 추천 엔진은 기존 규칙 기반 로직을 재사용한다. Spring AI가 이 요청에서 실행된다고 오해할 수 있는 문구는 제거했다.

## 입력 정책

- 이동 목적: 출근, 귀가, 약속, 여행, 기타 중 1개
- 이동 우선순위: 빠르게, 저렴하게, 덜 걷기, 혼잡 피하기 중 1개 이상
- 출발지와 도착지는 필수
- 기존 사용자 상태 및 이동수단 선호 입력 UI는 삭제하지 않고 비활성 흐름으로 보존

## API

기존 호환 API는 유지한다.

- `GET /api/v1/areas`
- `POST /api/v1/mobility-decisions`

Phase 2에서 다음 API를 추가했다.

- `GET /api/v1/mobility/context?originAreaCode={code}`
- `POST /api/v1/mobility/decisions`

현재 상황 API는 날씨, 혼잡, 도로 소통, 인근 지하철역 정보를 반환한다. 지하철 정보는 운행 상태가 아니라 인근 역 개수이므로 화면에서도 그렇게 표현한다.

## 백엔드 변경

- 새 요청 계약 `MobilityFlowRequest` 추가
- 현재 상황 응답 계약 `MobilityContextResponse` 추가
- 현재 상황 조회 유스케이스 `MobilityContextUseCase` 추가
- 기존 추천 서비스를 새 입력 계약에 맞춰 재사용
- 목적 및 우선순위 enum 확장
- 기존 추천 API를 유지한 채 v2 흐름 API 추가

목적 `OUTING`과 기존 선호 enum은 이전 클라이언트 호환을 위해 유지한다. 신규 화면에서는 사용하지 않는다.

## 프론트엔드 변경

- `MainPage`를 3단계 단일 페이지 흐름으로 개편
- 목적 선택기를 5개 목적에 맞게 변경
- 우선순위 선택기와 현재 상황 패널 추가
- 새 context 및 decision API 연결
- 결과 화면에 출발지와 도착지를 표시
- AI 분석 중이라는 부정확한 로딩·오류 문구 제거
- 중복 요청 방지를 위해 로딩 중 버튼을 비활성화

## 검증

- 백엔드 컴파일 성공
- 백엔드 기능 테스트 19개 클래스, 67개 테스트 통과
- Phase 2 Mobility 집중 테스트 20개 통과
- 프론트엔드 전체 테스트 9개 파일, 32개 테스트 통과
- 프론트엔드 프로덕션 빌드 성공

검증 범위에는 요청 변환, 필수값 방어, 현재 상황 API 계약, 새 추천 API 계약, enum 기반 추천 규칙, 현재 상황의 LIVE/STALE/UNAVAILABLE 표시가 포함된다.

## 알려진 한계와 후속 작업

- 경로별 실제 거리·시간·비용 계산은 아직 제공하지 않는다.
- 현재 추천 결과는 규칙 기반이며 Spring AI 호출 결과가 아니다.
- 출발지·도착지 후보 정규화, Evidence 모델, 저장/트랜잭션, SSE/Kafka, 캐시 개편은 Phase 3 이후 범위다.
- 백엔드 Security 설정의 `/api/**` 공개 범위는 별도 보안 단계에서 재검토해야 한다.
- 외부 데이터 장애 시 현재 상황 패널은 오류를 표시하고 재시도를 허용한다.

Phase 2 완료 지점에서 작업을 중단하며 Phase 3 기능은 구현하지 않는다.
